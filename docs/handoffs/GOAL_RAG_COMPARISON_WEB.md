## 目标与执行方式

在 `/Users/acerola/Dev/Python/RAG/env-rag-final` 和 `/Users/acerola/Dev/Python/RAG/LightRAG` 中，交付一个本机可启动的知识库问答网页：用户选择检索策略、输入自然语言问题、查看答案、完整原始 chunk 和文件来源，并可并排对照结果。重点证明 PG 路径能补足原 LightRAG local 的枚举漏项。

持续完成现状调查、实现、诊断、修复和验收。不要仅交付计划、Python helper、独立 CLI、静态页面或大量审计报告。允许在此范围修改代码；不要求用户每个小检查点转发交接。遵循适用 AGENTS.md；存在 `.codegraph/` 时先用 CodeGraph。先读 ENUMERATION.md、docs/retrieval/ENUMERATION_NEXT_STEPS.md 和 enum-entry-20261010-r1/report.md，核对当前实现，不能把历史报告当当前状态。

## 1. 策略选择与真实模式

网页支持：

- LightRAG 独立：naive、local、global、hybrid、mix。
- PG 独立。
- 组合：PG＋naive、PG＋local、PG＋global、PG＋hybrid、PG＋mix。
- bypass 单独标为“纯 LLM、不检索”的可选对照，无 chunk 时如实说明。PG＋bypass 等同 PG 检索后生成，不另造组合。

支持单策略运行，也支持勾选多策略对同一个问题并排执行。只运行已选策略，默认不勾全部；显示预计请求构成并防止重复提交。页面应显示实际执行策略，绝不能把 local 换个标签伪装成 mix/global 等。

原生模式优先调用原公开查询接口，使用真实对应后端。静态追踪查询链、版本和运行配置。结构化检索、生成、引用必须来自同一次检索记录：不得先取一批 chunk 展示，再重新检索另一批用于生成。若需要适配内部读取函数，复用该模式真实函数本体，记录语义差异；不得把自研替代路径冒充未改动原 API 基线。

优先复用已经运行的原服务；若需新增服务，使用独立只读适配，不通过存储初始化触发 DDL。配置或后端缺失时明确显示不可用，不填 fixture 结果，不静默换模型。

## 2. 真正的组合检索

同一问题分别取得所选 LightRAG 模式与 PG 的证据，再核对身份、去重、组装上下文，最后最多一次统一生成。不能把两份已生成答案拼起来当融合。

chunk 按真实 workspace＋chunk_id 去重，同一正文不同文档/版本不能误合并。实体、关系、文档、章节和表格目标保留类型。保留全部来源路径和原始分数口径，不直接相加不可比的分数。图谱实体/关系也作为证据展示，不能只剩 chunk 而丢掉 global/mix 的图谱上下文。

PG 的关键词发现与已确认范围分开。明确标准、版本、章节、表格或文件谓词时，复用目录确认、完整分页/续片展开及独立回读；top-k 只限制发现，不定义完整清单。一般问题允许 PG 作为关键词证据通道，但不得因无法做枚举就整题拒答或过滤掉所有 LightRAG 证据。

枚举范围不明确时提供真实候选和澄清选择；选择后继续同一问题。不能把发现晋升为确认目标，不以邻近版本替代缺失版本。两路失败、缺失、预算耗尽、上下文截断分别记录，不把降级结果称为完整双路检索。

## 3. 页面必备功能

1. 策略选择、问题输入、提交、加载/失败状态、耗时和结果状态。以同一个问题并排展示各策略答案，原生模式与组合模式标签明确。
2. “只检索/生成回答”开关。只检索不调用答案 LLM，但界面明确说明抽词或 embedding 仍可能调用服务。生成时不重复总结已经生成的答案。
3. 原始证据面板：完整 chunk、chunk ID、文档名、实际可得的章节/页码/表片定位，以及 LightRAG/PG/共同命中标记。完整文本可展开或分页展示，不用摘要冒充全文。
4. 答案引用可点击，定位到本次使用的来源。区分发现候选、合并证据、最终送入模型的证据和范围展开结果；标明未采用/被预算排除的内容及原因。图谱实体和关系单独可查看。
5. 文件来源：区分原始 PDF、解析文本和 chunk。文件存在且访问允许时可预览/下载；否则明确标注不可用。只允许知识库目录白名单，防止任意本机文件访问。

允许导出本次结果与证据 JSON，用不存在的新文件/目录保存。保留问题、策略、参数、检索记录 ID、内容哈希、引用映射、模型、调用量及各阶段耗时。没有单独测量的阶段写 unavailable，不靠减法制造精度。

服务默认只绑定本机地址，密钥/DSN 不进入浏览器、导出和日志。界面用中文、清晰易用、桌面可读；参考适用前端设计技能，控制实现规模，不建设账户、上传、入库或后台管理系统。

## 4. LLM 回答与清单保真

原生独立模式保留对应的原回答流程。组合模式以本次合并证据统一生成；PG 独立允许只展示清单，也允许基于本次证据总结。使用当前配置模型，不改 .env、不静默替换。

枚举清单作为独立结构化交付保留，LLM 总结不得删改清单或把 partial/ambiguous/missing 升为 complete。模型输出与检索完整性分开标注，禁止拿引用真实自动证明整句声明正确。

引用只允许本次实际使用的证据 ID；核验文档、版本和原文支持，特别核对数值、单位、等级、平均时间、正文与资料性附录的区别。总结允许有依据的改述，不能无依据补事实。引用失败或生成失败留证，不自动补问模型。不要为过关删除既有来源核验；需要调整旧保守声明合同时，先明确新旧差异并加入必要正负例。

对照时提供统一生成参数的实验口径，与保留原生提示的产品口径分列。不能把提示/模型/上下文预算同时变化的答案差异全部归功于 PG。

## 5. 验收与修复循环

先完成离线实现与必要测试，再冻结现场验收矩阵。12 道枚举题＝6 道已有验证题＋6 道来自其他文档的新题；另有 8 道一般问答/歧义控制题。新题独立从原文确定期望完整集合，覆盖真实问法、文件、条款、续表、版本及范围确认；不能按 PG 是否能答对挑题，运行后不得换题或缩分母。

重点对比真实原 local 与 local＋PG，逐题交付原问题、预期、两个答案、缺项、多项、文档/版本错误、引用、时延及成本。保留两者都对/仅增强对/仅 local 对/两者都错。旧共用答题流程的 local 和历史回放不能冒充原系统现场基线。

建议质量门槛：至少修正 3 道原 local 的真实集合错误；原 local 已正确的枚举题不新增集合错误；8 道控制题不误作完整清单；现有已验收能力不回退。若固定题组没有足够 local 失败，结论必须是样本不足以证明互补，不能换题凑增益。

其余模式/组合分别完成必要离线合同测试及至少一次有界现场功能验证。确认真实模式 dispatch、原始证据、生成开关、引用和降级路径；不能仅验证选项可点击。本轮不扩大为所有模式全面质量评测。

每次修当前最主要失败类别，再复验相关题与必要控制。禁止题号硬编码、金标注入、全拒绝、挑题、放宽来源或掩盖失败。已审且字节未变的部分不反复全量审；冻结规则在实施前明确，避免无限追加验收导致项目失控。

浏览器现场验收必须覆盖启动、提问、模式切换、多策略并排、生成开关、证据展开、引用定位、澄清选择和错误状态，保留必要截图。自动测试不能代替实际网页操作。

## 6. 调用授权与预算

授权本 Goal 范围的实现、必要测试、现有服务只读访问及有界真实对照。40 次真实 LightRAG 检索执行由所有原生/组合模式共享；40 不是每个模式各 40。优先固定原 local 基线 20 次，其余用于模式功能核验和有依据的失败复验。组合每执行一遍 LightRAG，也扣一次。可以共享本轮同问题、同参数的已取得检索记录供对照，但必须显式标 reused，不声称独立 fresh。

答案生成总上限 60 次，包含原生和组合/PG 的回答；其中组合/PG 额外生成最多 20 次。bypass 也计入答案预算。keyword LLM 最多 40 次，embedding 最多 160 批；单批最多 32 文本，单批字符上限在离线核对既有服务合同后预先固定，不允许无限批次。所有失败请求计入预算，不自动重试。预算是共享上限，不保证或强迫必须用完。

本轮不新增精排组件，网页精排默认关闭，实验各路保持一致并显式记录；不声称该设置等于用户原系统全部默认配置。需要原配置精排的额外现场对照，先交付具体必要性与预算，不静默增加调用。

调用前预留配额，实发另记；拒绝、未发出、已执行后失败分开。被底层吞掉的预算异常也必须在结果体现。运行开始前核验配置、身份与预算，运行后检测漂移。并排执行限制并发，防止按钮、重渲染或重连重复消费。

预算耗尽时继续完成可离线完成的工作，停止新增真实请求。未达到质量门槛不能宣布成功，不自动追加额度或重新开启全量两轮评测。

## 7. 数据与代码保护

不写生产数据库，不执行存储 initialize、DDL、入库、索引/目录重建或语料重新 embedding；不写答案/抽词缓存。复用已运行服务；允许按项目已有规程恢复现有容器，但不重建卷或初始化存储。若无法在只读边界内获得真正原系统基线，完成其余工作、明确阻碍，不用替代链路假冒。

不修改 .env、gold、历史代次、冻结测试或旧清单。保留用户工作，不自动 commit/push/deploy，不默认启用融合。新证据独立目录、不可覆盖；保护清单初末核对，避免每次小修改都重扫全部历史。必要兼容缝要明确记录，旧断言不能删弱化。

## 8. 子智能体分工

微小、独立、可并行的事项交给 GPT-6 Luna 子智能体，reasoning effort=max，例如一个接入点调查、少量原文预期核对、独立组件或明确测试。控制并发和上下文，不为了并行拆碎核心逻辑，不让多个智能体改同一文件。

主 agent 负责策略合同、核心融合/范围语义、整合、实际浏览器检查、独立答案核对与最终裁决。子智能体“测试通过”不能代替主 agent 验收真实输出。
