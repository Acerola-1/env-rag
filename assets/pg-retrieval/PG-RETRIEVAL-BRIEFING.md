# PG 检索路技术汇报（env-rag / PostgreSQL 结构化检索路）

> 面向技术组长的口头汇报稿。PPT 取第一节；发言稿按"❓ 提问 → 口径"组织，含追问预演。
> 所有数字均出自仓库事实：`openspec/changes/add-pg-scoped-retrieval/design.md`、`docs/initialization/INGESTION.md`、`ENUMERATION.md`、`reports/pg-retrieval/`。

## 一、30 秒定稿版（PPT 用）

环境知识库检索系统（Python），LightRAG 双路对照中的 PostgreSQL 结构化检索路。动机：原 LightRAG 是**知识图谱检索**，按实体和语义相关性带回答案片段，解决不了"列出 GB8978-1996 表1 全部项目及限值"这类**枚举题**——排序再准也保证不了"全部"。做法：不重新解析文档，复用 LightRAG 已入库的原文和检索块、加上 MinerU 的文档结构产物，在 PG 里派生出一条"文档 → 章节 → 表格 → 原始块"的结构目录，再配应用侧中文分词的全文索引。查询五步：标准号精确定位、版本严格匹配绝不替代、关键词分级召回、范围确认后成员全读——**top-k 只限制发现，枚举清单永不被截断**。这一路全程零模型调用；效果由冻结评测背书：45+30 道冻结金标、召回达标、编号查询 100%、反例零误判；融合对照未达标，失败如实保留、不强行启用。

## 二、发言稿

### 1. 为什么要再造一路检索

❓ "已经有 LightRAG 的向量 + 图谱检索了，为什么还要在 PG 上做一路？"

口径："动机不是性能，是**能力边界**。原 LightRAG local 路是**知识图谱检索**：用 LLM 从文档抽取实体和关系建图谱，查询时按实体、关系带回相关子图（实体/关系的召回底层有向量参与，但检索范式是图谱，口径统一叫知识图谱检索，和 naive 的纯向量模式区分开）。它擅长'找相关的'，天然不擅长'给全部的'。环保知识库的高频问题恰恰是枚举题：列出 GB8978-1996 表1 的全部 13 项限值、列出 4.2 节的全部条款、列出库内某个标准的全部版本文件。这类题在图谱路上有可复现的漏项——带回来的永远是"语义相关的有限片段"，排序再好，第 14 名永远进不了上下文。我们的思路是把'完整'从**排序质量的概率问题**变成**数据结构的确定性问题**：表号 → 逻辑表 → 有序成员清单 → 成员全读。PG 这一路和图谱路是互补定位：可确认范围的枚举/事实题走 PG，语义泛化问答留给 LightRAG。"

### 2. 数据侧：不动原文，只建派生

❓ "数据从哪来？切块是谁做的？"

口径："切块不在我们代码里，**我们一行 chunking 代码都没有**。语料是 230 份环境标准 PDF，MinerU 负责解析产出结构化产物，LightRAG（lightrag-hku，uv.lock 锁定 1.5.7）的入库管线负责切块并写入 `public.lightrag_doc_full` / `doc_chunks` / `doc_status`——default workspace 现有 221 份整篇文档、5709 个 chunk。PG 这一路对这三张表**严格只读**：连接统一 `readonly + repeatable_read`，任何 DDL 都不允许引用它们。"

❓ "那你们自己的表存什么？"

口径："自有 `env_rag` schema 建两层派生。**目录层**是骨架：`documents` 存每份文档的自身编号/版本/标题（字段级溯源）；`source_units` 存 MinerU 解析出的原始块和表格**定位器**——只存定位信息不存正文，正文永远以磁盘上的解析产物为单一来源；`unit_chunk_links` 是缝合点，把原始块/表格多对多挂到 chunk 上（依据 sidecar 引用或内嵌表格 ID，匹配依据落库可审计）；`scopes/scope_units` 存章节、条款、逻辑表的范围和有序成员。**检索层**就是两张 tsvector 表 + GIN 索引。构建时缺解析产物直接拒绝发布——宁可报错，不出'静默缺口的完整目录'。"

❓ "怎么保证派生数据和来源永远一致？"

口径："一套**指纹冻结 + stale 语义**。来源指纹是 composite SHA-256，五个组件：PG 原文全字段、chunks 的 id/顺序/正文/heading/sidecar、doc_status、MinerU 产物的**字节级 SHA**、分块参数——任何一样变了指纹就变。构建前、查询前、返回前**三次**核对身份，不符一律标 `stale` 拒绝服务，不沿用旧定位。所以加新文档后系统会'变砖'，这是设计行为：派生数据永远不许在来源不明的情况下冒充可信答案。"

### 3. 中文全文检索：应用侧分词

❓ "为什么不用 PG 原生中文方案，或者上 ES？"

口径："PG 默认 `to_tsvector` 对中文完全失配——整句当一个 token，生产实测不可用，这条捷径直接排除。两个备选的取舍：上 ES 要引入一整套服务镜像和同步链路，语料规模只有 5709 个 chunk，收益撑不起运维成本；数据库中文扩展会耦合服务镜像。所以选**应用侧分词**：jieba 0.42.1 固定版本、关 HMM（纯词典、确定性），配一份受控环保词表，分完词以空白连接，PG 侧永远 `to_tsvector('simple', …)` + GIN，排序 `ts_rank_cd`。分词器版本、词表 SHA、清洗版本全部参与索引身份——改词表就生成新索引、原子切换，绝不静默复用旧索引。"

❓ "标准号、条款号这些怎么保证不被切碎？"

口径："这是整个分词的核心技巧：**保护跨度**。正则先'圈出'不能被分词器碰的东西——带年份标准号、裸标准号、条款号、pm2.5 这类字母数字复合词、表号——圈完的跨度直接归一化成规范词位，剩下的区间才交给 jieba。效果是 `GB 3095—2012`、全角 `ＧＢ３０９５－２０１２`、`gb3095/2012` 三种写法归一到同一个相邻短语 `gb3095 <-> -2012`；`GB14554-93` 和 `GB14554-1993` 等价匹配。另外索引侧是查询侧的**超集**：索引用 `cut_for_search`（最大词 + 字典子词都进索引），查询用 `lcut`（只最大词），从构造上保证查询侧任何词在索引里必然存在——这是单向的召回保证。"

### 4. 查询执行：五步路由 + 有记录的放松阶梯

❓ "一次查询具体怎么走？"

口径："设计顺序是**编号定位 → 元数据限定 → 关键词候选 → 范围确认 → 完整展开**。第一步：题面里抽标准号，按 `self_code` 在文档级索引**精确**匹配，版本缺了就报 `missing`——绝不用邻近版本替代，2/4 位年份等价是唯一放宽。第二步：编号一旦命中，后续关键词检索**限制在这些文档内**——强约束是元数据，不是 top-k 排序。第三步：关键词候选，跑一个有记录的放松阶梯。第四步：题面带表号/章节时，绑定到目录里真实存在的范围。第五步：完整展开，等下单独讲。"

❓ "关键词查不到怎么办？怎么保证不静默降级？"

口径："放松阶梯每一级都**落 trace**：A 全词 AND → B 语料里不存在的词（OOV）先拿受控同义词组 OR 试 → C 只用出现过的词做 AND → D OR 兜底。每一级把确切 tsquery、命中数、应用了哪些同义词写进结果。关键规则是：OOV 概念不许被悄悄丢掉——它的同义词组必须在返回任何核心结果之前先试（G2-6）；同时放松永远不碰强约束，编号和版本由路由强制，关键词再怎么放松也替代不了。所以每份答案都能回答'你是严格 AND 来的还是放松到 OR 来的'，审计可回放。"

### 5. 枚举完整性：top-k 只管发现，不管清单

❓ "'列出全部'怎么保证真的全？top-k 截断了怎么办？"

口径："架构上把检索拆成**两段式**：发现段和读取段。发现段有 top-k 预算，负责把'候选范围'找出来；范围确认之后进入读取段——**成员全读**，稳定分页、续表跨 chunk 完整拼读、条款逐条读，这一段永不被 top-k 截断。真实例子：GB8978-1996 表1 有 13 行，物理上是两个续表片（1–4 行、5–13 行）映射到 chunk；候选预算设 1，依然 complete 返回全部 13 行、每行带原始行号引用。完整性不是'多给点预算'，是**先确认结构、再全量读成员**。"

❓ "那结果的'complete'可信吗？"

口径："状态语义是显式声明的，五个值：`complete`（确认范围内成员全读、条目有核验引用）、`partial`（缺成员/缺条款/引用未过）、`ambiguous`（范围或续片归组无法确认）、`missing`（明确目标缺失）、`stale`（来源/目录/索引身份变化）。complete 只承诺'已验证的目标范围覆盖'，不承诺 PDF 解析无损——这个边界写进文档。每条目的引用绑定到原始 unit/chunk ID 和逐字引句，正文主张只接受来源连续片段，应用侧只允许年份前缀和标点装饰，改写过的引用直接拒收。"

### 6. 效果验证：冻结评测合同（含最值钱的失败）

❓ "效果怎么证明？"

口径："不靠感觉，靠**先冻结后评测**的合同。Phase 0 只读审计建立事实合同，金标在运行前冻结（45 道正例 + 30 道反例，绑定来源指纹，覆盖同名不同年份、续表跨片、正文跨 chunk、缺版本、长范围超时这些难例）。硬门槛：候选证据 recall@20 ≥ 0.90、编号/版本查询 100% 正确、**所有反例零 false complete**——'看起来答对了但范围错了'是红线。枚举入口现场逐例验证：6 个完整集合正例（2/3/4/4/13/1 项）、1 个表格归组歧义、1 个跨标准判断题读前拒绝；工程回归 550 项通过。"

❓ "最后整体效果怎么样？"

口径："如实说，**分两半**。PG 独立路的枚举和引用完整性验证达标；但 Gate 4 的正式两轮对照——'PG+local 融合整体优于 local'——**没有通过**。我们的处理是保留失败报告、默认路径维持已验证基线、不强行启用融合，失败事实和逐题证据都留在 reports 里可查。这个项目的质量纪律比结论本身值钱：小样本指标不外推生产规模，答案成功不升级 complete，模型失败不冒充成功。"

### 7. 运维：加新资料是三步半自动

❓ "以后补新文档流程是什么？"

口径："解析切块全自动交给 LightRAG 入库管线（含 MinerU，会产生 embedding 费用）；PG 这边是**半自动**——来源一变，指纹失配，所有查询显式 stale，需要人工执行：重算并确认新来源指纹 → `catalog-build --fingerprint <新指纹>` → `search-build`，旧快照自动退役、新快照原子切换。两个坑提前说：MinerU 解析/sidecar 配置必须和现存产物一致，否则块到 chunk 的映射依据对不上；新文档缺 `.parsed` 目录会直接拒绝构建。这套'变砖'流程换来的是：任何时候库里没有一份说不清来源的派生数据。"

## 四、一句话收尾

> PG 这一路做了一件事：**把"标准号 → 文档 → 章节/表格范围 → 原始单元"这条结构链固化进数据库，让"全部"从概率问题变成结构问题**——零模型成本、可审计、引用逐字可核验，和知识图谱检索路互补成双路对照体系。
