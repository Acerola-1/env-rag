# 下一步：把枚举能力变成 LightRAG 可用的补充

本计划以当前代码、枚举入口报告及最终结案记录为依据。目标不是重新证明整个混合系统优越，而是证明并交付：同一个提问入口，在原 local 漏清单成员的题上，能够通过目录确认与完整读取补齐答案。

## 当前事实

- `ask` 已在六个完整集合正例上验证，另有两个歧义/非枚举控制例。文件、条款、续表均可独立回读。
- Python bridge 开启时直接走枚举，关闭时委托原 `rag.aquery`。原 REST/WebUI 尚未接入；这不是已经部署的增强功能。
- 旧评测 local 使用了共用的新答题流程，不等同于原 LightRAG 的未改动 local API。
- 旧 Gate4 未通过，不能据此推导“PG 无法补足原 local”。同样，六个正例也不能推导原系统整体改善。

## 1. 先完成接入与问题范围确认

先静态追踪实际使用的 LightRAG 查询入口及其配置，确定一个接入点，保留现有关闭行为。提供“清单增强”显式开关；自动选择作为后续能力，不先修改默认路径。

输出三个明确分支：

1. 文件/条款/表格清单，且文档、版本、范围可确认：走 `ask`，保留完整集合与引用，直接呈现，不交给模型重新删改条目。
2. 清单问题但目标不明确：给出可选择的真实文件/版本/章节，补充选择后再执行。候选只能供选择，不能自己晋升为确认范围。失败、缺失和部分结果仍保留其状态，不静默回退为完整答案。
3. 一般解释、比较、判断：交回原 local；不能把“不是枚举”当成整个产品拒答。例如两表是否相同不能用两表的行清单代答。

现有 `ask` 的受控语法、要求明确文件/范围，以及关键词式非枚举拒绝，是需要改善的用户入口边界；不是重新建设索引的理由。

离线验收：关闭开关的参数/返回/异常行为保持；三分支及澄清后续请求各有正负例；通用问答没有被清单路由截走；partial 不会在格式化中变成 complete。先核对入口合同并做离线实现，不新增付费调用。

## 2. 用原 local 做小规模同题对照

运行前固定 12 道枚举题（六道当前已验证题 + 六道来自其他文档的新题）及 8 道一般问答/歧义控制题。新题从原始文件独立列出正确集合，再运行；不按 PG 能否答对筛题，也不只保留 local 失败题。新题同时包括缺标准号、名称定位、续表、不同版本等真实问法。

比较对象必须是原 LightRAG 实际 `local` 查询与开启增强后的同一入口。记下版本、提示、配置、缓存设置和实际调用；不借用旧评测 local 或旧答案代替原基线。

每题报告：local 原答案、增强答案、期望集合、缺项、多项、文档/版本错误、引用支持、时延和调用数。保留四种结果：两者都对、只增强对、只 local 对、两者都错。一般问题还要核对分流行为及是否新增请求。

预先验收目标：12 道中至少 3 道原 local 存在的集合错误被增强修正，原 local 已正确的枚举题不得新增集合错误，8 道控制题不得被误作完整清单。此为小样本接入门槛，不是全库改善率；若原 local 没有足够失败样本，如实结论为当前样本不足以证明互补，不另挑失败题冒充原组。

真实原 local 请求会消耗模型/embedding 额度，须在具体矩阵、单次运行预算和调用路径可审查后安排。本计划不执行、不增加任何既有付费授权。

## 3. 每次只优化实测最主要的失败层

- 找不到目标：改名称/别名与问题要素解析，输出解析证据；不以模型猜测替代身份核对。
- 范围不明：补章节标题确认与交互澄清，不截取 top-k 当全集。
- 条目漏、多、串版本：改归属、结构边界或续表关联，并用失败题的原输入与独立期望验收。
- 来源缺失或解析损坏：记录数据缺口，单独安排修复；不靠放宽引用验证过关。
- 清单已经正确：直接结构化呈现，避免无必要的合成改写。跨文件解释另行设计，不混入本轮枚举门槛。

一次处理一个失败类别，复验该类别及必要控制例；通过后停止重复审相同字节。评分标准和主要预期在实施前固定，新发现问题按会造成的实际错误分级，不把每个边界都升级成整项重新开工。

## 收尾条件与成本边界

交付实际可用入口、可关闭增强、同题缺项对照及明确适用范围。小组未达标时交付主要失败原因与一个有依据的下一项改动，不自动重开两轮全量评测或通用融合。

本次计划准备只读取文件；未改源码、原项目、配置、数据库、历史报告、gold 或冻结测试，未调用模型。语料文件占比不是互补收益：是否适合 PG 取决于问题及其可确认范围，必须按查询任务分类，不把标准 PDF 的数量直接换成可解决问题占比。
